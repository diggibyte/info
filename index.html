Employee Upskilling Program

8 weeks to build with agentic AI, not just talk about it.

Every team here already knows how to build reliable systems: that is the job. What is changing is the tooling. Agentic AI is becoming a normal part of how that work gets done, not an experiment on the side. This program exists so that shift happens deliberately, with real skill behind it, instead of piecemeal and reactive.

The goal is not to make everyone an AI researcher. It is to make sure that when a customer asks if something can be faster, cheaper, or more reliable, the answer is yes, because the team building it knows how to put agents to work on real data, real pipelines, and real decisions, safely and with the right guardrails in place.

A hands-on program for Data Engineering, AI/ML, BI, and Platform teams. Every week ends with something working: not a slide, an artifact you actually built, in a repo someone else can run.

The Weekly Journey

Every week has a clear objective: learn one capability, ship one working artifact, and leave evidence behind. Artifacts live in your fork of the track starter repo and are reviewed by pull request, not by screenshot.

Phase 0 · Week 0
Setup and Baseline~2 hrs · before Week 1

This week exists because the most common way a program like this fails is that people spend Week 1 raising access tickets and Week 8 unable to prove anything changed. Complete every item below before the cohort starts.

1. Access

  • Databricks sandbox workspace, with your own Unity Catalog schema under the training catalog and a compute policy attached.
  • A model serving budget and an AI Gateway rate limit set against your identity, so cost is visible from day one rather than discovered in Week 6.
  • Claude Code seat, GitHub org membership, and a fork of your track starter repo.
  • Access to the Databricks managed MCP servers in the sandbox workspace.

2. Toolchain install

  • Databricks CLI, authenticated to the sandbox workspace.
  • Databricks AI Dev Kit: the MCP server plus the Databricks agent skills, installed into your IDE agent.
  • Databricks Asset Bundles validated locally against the starter repo, so everything you build this program is deployable from the start.

3. Data rules

  • Each track has one approved sandbox dataset. Use it.
  • No customer data, customer documents, customer credentials, or customer source code goes into any prompt, notebook, repo, or model endpoint at any point in this program, regardless of which model or tool is being used.
  • If your Week 7 use case needs customer context, it is replaced with the synthetic equivalent or the use case is changed. This is not negotiable and is checked at review.

4. Baseline capture

  • Record the before numbers for the task you intend to improve: hours per week spent on it, defects caught in review over the last four sprints, and typical turnaround time.
  • Commit these to baseline.md in your fork in Week 0. Week 8 impact is measured against this file. There is no way to reconstruct it later.

5. Time commitment

  • Confirm with your reporting manager that 5 to 6 hours per week are protected and booked against the L&D code.
  • If delivery pressure takes a week from you, tell your track mentor the same week. One week can be recovered; three cannot.
Week 0 outcome: a working environment, an approved dataset, and a committed baseline.md. Participants without all three do not start Week 1.
Phase 1 · Weeks 1-3
Core FoundationAll roles

These three weeks create the same baseline for everyone. By the end of Week 3, every participant has the shared AI skills needed to confidently move into a role-specific build, and has measured their own work at least once.

Week 1: AI-Native Ways of Working · ~5 hrs

Claude Code 101 Claude Platform 101
  • Learn: prompting, context engineering, secure coding practices with AI tools, and what must never be pasted into a model.
  • Hands-on: connect the Databricks AI Dev Kit MCP server to your IDE agent, then run the same real backlog task twice: once without tool access, once with. Record what changed in the output quality.
  • Ship: one merged pull request authored with an AI assistant, plus a short note in the repo on where the assistant helped and where it was confidently wrong.
  • Cost: record your week-1 token and DBU spend. You will need the trend line in Week 8.
  • Evidence for: AI adoption and enablement.

Week 2: Retrieval and Evaluation · ~6 hrs

Building RAG Agents
  • Learn: embeddings, chunking, Databricks AI Search, Agent Bricks Knowledge Assistant, structured outputs, and model selection.
  • Build: a retrieval application over the approved sandbox document set.
  • Build, not optional: a 15-question evaluation set with expected answers, scored in MLflow 3 before you tune anything. Retrieval that is not measured is a demo, not an engineering artifact.
  • Ship: repo containing the app, the eval set, and the first eval run with its baseline score.
  • Evidence for: technical defense.

Week 3: Agents, Tools and Memory · ~6 hrs

MCP Intro MCP Advanced Databricks Agentic Apps
  • Learn: agent design patterns, tool calling, MCP, state and memory with Lakebase, and human-in-the-loop controls.
  • Build: an agent that calls at least three tools, of which one is a Unity Catalog function and one is a Databricks managed MCP server, so the agent reads real context from your environment instead of acting in a vacuum.
  • Build: put one write-capable or destructive action behind an explicit approval gate. An agent that can change state without a gate does not pass review.
  • Ship: the agent plus MLflow traces showing the tool path for three real questions.
  • Evidence for: technical defense, governance and security.
Phase outcome: three working artifacts in a repo - an AI-assisted merged PR, a measured retrieval app, and a gated 3-tool agent with traces.
Phase 2 · Weeks 4-5
Role SpecializationYour role track

Weeks 4 and 5 are where the program becomes specific to what a Data Engineer, BI Engineer, Data Scientist, or Platform Engineer actually needs to deliver. The real problem is chosen here, in Week 4, not in Week 7, so that nothing gets rebuilt later.

Week 4: Design and Use Case Selection · ~5 hrs

  • Learn: the domain patterns for your role, listed in your track card below.
  • Do: pick your Week 7 problem now, from the curated use case backlog, with the manager or PM who owns it. Get their agreement in writing that they will spend 30 minutes with you in Week 7.
  • Build: a one-page design covering tools, data sources, auth model, failure modes, approval gates, eval criteria, and a cost ceiling.
  • Gate: your track mentor reviews the design before you write implementation code. No design review, no Week 5.

Week 5: Role Agent Implementation · ~6 hrs

  • Build: the working, role-specific agent from your Week 4 design, aimed at the real problem you chose.
  • Ship: agent deployed to the sandbox through Databricks Asset Bundles, from the repo, not from the workspace UI.
  • Definition of done: it runs end to end unattended, it is deployable by someone else with databricks bundle deploy, and the eval set from Week 2 has been extended to cover it.
  • Evaluate: this is the artifact you carry into Weeks 6-8. It does not get rebuilt later, only strengthened.
Phase outcome: a deployable agent that solves a named stakeholder's real problem, not a generic exercise.
Phase 3 · Weeks 6-7
Production and Real-World ApplicationShared process

This is where the work becomes trustworthy, measurable, and useful outside a lab. The goal is not a demo; it is a governed system that solves a real stakeholder problem and survives someone trying to break it.

Week 6: Trust, Security and Cost · ~6 hrs

Deploy & Monitor
  • Learn: LLM judges and evaluation methodology, guardrails, Unity Catalog permissions and lineage for agent tools, PII handling, MLflow 3 tracing, AI Gateway rate limiting and model routing, and cost attribution.
  • Build: expand the eval set to 30 cases including adversarial ones; add guardrails; run the agent under a least-privilege service principal scoped in Unity Catalog; add a cost and latency view.
  • Red team, in pairs: swap agents with another participant and try to make theirs leak data it should not return, call a tool outside its scope, or follow instructions planted inside a retrieved document. Write up what you found, then fix what was found in yours.
  • Why this is here: we deploy agents against customer data for a living. Prompt injection, over-broad tool scopes, and secrets in prompts are the failure modes that end engagements, and they are the ones nobody practises.
  • Evidence for: governance and security, cost control.

Week 7: Stakeholder Sprint · ~6 hrs

  • Do: run your agent against the problem you picked in Week 4, with the stakeholder in the loop, not as an observer at the end.
  • Ship: measured before-and-after against baseline.md, plus written confirmation from the stakeholder that it helped.
  • Ship: a handover README complete enough that another engineer can run the agent without asking you a single question. This is tested literally: a peer clones it and runs it.
  • Evidence for: stakeholder value, delivery improvement, knowledge sharing.
Phase outcome: your agent is measured, hardened against a real attempt to break it, and validated by the person whose problem it solves.
Phase 4 · Week 8
Review and ShowcaseFinal proof

Week 8 is where you present the evidence that your work matters. This is not an attendance check; it is a demonstration of impact and technical judgment.

Submit 48 hours before your slot

  • Repository link, baseline.md and the after numbers, eval report, sample MLflow traces, cost and latency view, red-team findings and fixes, stakeholder confirmation, and the handover README.
  • Reviewers read the evidence pack before the session. The demo is for the things a document cannot show.

On the day

  • Do: a live 15 minute session - 10 minutes running the real system, 5 minutes of questions. No slides, no screenshots, no recordings.
  • Defend: model selection, tool boundaries, what happens when it fails, what you would build differently with another two weeks.
  • Outcome: a recognition tier assigned on demonstrated impact, not attendance.
Outcome: a credible, measurable demo backed by artifacts, design decisions, and real stakeholder value.

Weeks 4-5 · Role Tracks

Same two weeks, different destination. Pick the track that matches your role and the outcome you need to ship.

Shared Toolchain
Every track, no exceptions

All four tracks, Platform included, use the same toolchain so that work is portable between people and reviewable by anyone. Set this up in Week 0.

Mandatory: Databricks AI Dev Kit - the MCP server plus the Databricks agent skills, installed into your IDE agent; MCP configured in VS Code, Claude Code or equivalent; Databricks CLI and Asset Bundles; MLflow 3 tracing on every agent run; and the governance module for whichever model provider your stack uses.
Where it lives: databricks-solutions/ai-dev-kit and the MCP on Databricks documentation. It is a toolkit you install and use every week, not a course you complete once.
Data Engineers
→ Agentic Data Engineers

What you will learn

  • MCP and tool development
  • Lakeflow Connect and Spark Declarative Pipelines
  • Structured and unstructured ingestion
  • Metadata, lineage and context engineering
  • Unity Catalog governance and data quality expectations
  • Automated data-quality agents
What good looks like
  • You can connect an agent to real data sources and tools without losing control of the workflow.
  • Your agent detects pipeline issues, explains likely root cause, and proposes remediation that a human approves before it runs.
  • You understand lineage, quality checks, access boundaries, and the cost of each action.
Mandatory: shared toolchain, plus Unity Catalog lineage and Lakeflow Jobs run history as agent tools.
Build: a pipeline triage agent that detects failures, reads lineage and quality results, diagnoses likely root cause, and proposes remediation. Any action that writes or repairs runs only behind an approval gate.
Evaluate: did the agent act on the right signal, reduce manual triage time against your baseline, and explain the decision path clearly?
Data Scientists
→ Agentic AI Engineers

What you will learn

  • Databricks AI Search, embeddings and reranking
  • Tool calling and memory with Lakebase
  • Mosaic AI Agent Framework and multi-agent patterns
  • Model selection and routing
  • Evaluation, LLM judges and hallucination testing
  • Guardrails and MLflow 3
What good looks like
  • Your agent answers real business questions with grounded evidence and clear reasoning.
  • You can validate model output against source facts and explain the answer path.
  • Your workflow is measurable: accuracy, grounding, explainability, and usefulness all have numbers attached.
Mandatory: shared toolchain, plus a Genie space or Unity Catalog functions exposed as agent tools.
Build: a multi-agent business analyst - planner, researcher or data agent, reasoning agent, and a validation agent that can reject the answer.
Evaluate: scored against your 30-case eval set, how accurate, grounded and explainable is the final answer on real business questions?
BI Engineers
→ AI/BI Engineers

What you will learn

  • Unity Catalog metric views and trusted metrics
  • Genie spaces and AI/BI dashboards
  • Natural language to SQL validation
  • Conversational analytics
  • Proactive insight generation
  • Action-oriented analytical agents
What good looks like
  • Your agent can answer a business question in plain language and tie the answer back to a governed metric definition.
  • The answer explains the business story instead of only showing a chart or table.
  • A stakeholder can trust the result without needing a data analyst to validate every step.
Mandatory: shared toolchain, plus at least one Unity Catalog metric view backing the agent's numbers.
Build: an agent that answers questions like "why did gross margin decline?" by investigating drivers, explaining the trend, and recommending next steps. Every number it returns must name the metric view it came from.
Evaluate: could a business stakeholder trust the answer without needing a data analyst to validate every step?
Platform Engineers
→ Agentic Platform Engineers

What you will learn

  • Mosaic AI Model Serving and AI Gateway
  • Managed and custom MCP servers on Databricks Apps
  • Identity, service principals and on-behalf-of authorization
  • Unity Catalog governance and secrets
  • Asset Bundles, CI/CD, tracing and observability
  • Model routing, cost attribution and agent operations
What good looks like
  • Your solution is secure, observable, and ready for real team adoption.
  • You can explain access boundaries, model routing, logging, and operational guardrails.
  • You have built something reusable that helps other teams ship AI workflows more safely and consistently.
Mandatory: shared toolchain, plus a custom MCP server hosted as a Databricks App and a least-privilege service principal model.
Build: a reusable Agent Platform Blueprint, shipped as an Asset Bundle another Diggibyte team can deploy with one command, covering serving, gateway limits, tracing, secrets and cost attribution.
Evaluate: did another track actually deploy it, and does it keep model cost and access under control when they do?

Demonstrating Your Impact

Week 8 is not a scored exam. You show real, evidence-based impact across seven dimensions, reviewed live. Each dimension has a named artifact so there is no ambiguity about what counts.

DimensionWhat you must showEvidence artifact
Stakeholder value delivered A clear before and after picture: what changed for a customer or internal stakeholder because of what you built, in plain terms a non-technical reviewer can understand. baseline.md vs after numbers, plus written stakeholder confirmation
Delivery improvement Evidence that your work improved delivery quality: defects caught before release, review time saved, or turnaround reduced, measured against the numbers you recorded in Week 0. Baseline delta plus a reviewer or PM sign-off
AI adoption and enablement Proof that you applied AI-native practices in daily work, plus one contribution that spreads it: an internal session, a written guide, a blog post, or an external talk. Merged pull requests authored with an assistant, plus the session or post
Governance and security The access model your agent runs under, how PII is handled, what the approval gates cover, and what the red-team exercise found in your agent and how you fixed it. Unity Catalog permission model, guardrail config, red-team findings and fixes
Cost control How you measured token and DBU consumption, and the specific technique you applied to reduce it - prompt trimming, caching, smaller model routing, or batching - with the before and after numbers. Cost and latency view, with the week-1 to week-8 trend
Knowledge sharing Whether your work is documented clearly enough that another team member can run and extend it without asking you questions. Tested, not assumed. Handover README, plus a peer who cloned the repo and ran it
Technical defense Defend your design under questioning: model selection, tool boundaries, failure modes, and what you would do differently with more time. The live Q&A in your Week 8 session
